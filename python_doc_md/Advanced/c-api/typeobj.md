# Type Object Structures {#type-structs}

Perhaps one of the most important structures of the Python object system is the structure that defines a new type: the `PyTypeObject`{.interpreted-text role="c:type"} structure. Type objects can be handled using any of the `PyObject_*` or `PyType_*` functions, but do not offer much that\'s interesting to most Python applications. These objects are fundamental to how objects behave, so they are very important to the interpreter itself and to any extension module that implements new types.

Type objects are fairly large compared to most of the standard types. The reason for the size is that each type object stores a large number of values, mostly C function pointers, each of which implements a small part of the type\'s functionality. The fields of the type object are examined in detail in this section. The fields will be described in the order in which they occur in the structure.

In addition to the following quick reference, the `typedef-examples`{.interpreted-text role="ref"} section provides at-a-glance insight into the meaning and use of `PyTypeObject`{.interpreted-text role="c:type"}.

## PyObject Slots

The type object structure extends the `PyVarObject`{.interpreted-text role="c:type"} structure. The `~PyVarObject.ob_size`{.interpreted-text role="c:member"} field is used for dynamic types (created by `!type_new`{.interpreted-text role="c:func"}, usually called from a class statement). Note that `PyType_Type`{.interpreted-text role="c:data"} (the metatype) initializes `~PyTypeObject.tp_itemsize`{.interpreted-text role="c:member"}, which means that its instances (i.e. type objects) *must* have the `~PyVarObject.ob_size`{.interpreted-text role="c:member"} field.

`PyObject.ob_refcnt`{.interpreted-text role="c:member"}

> The type object\'s reference count is initialized to `1` by the `PyObject_HEAD_INIT` macro. Note that for `statically allocated type
> objects <static-types>`{.interpreted-text role="ref"}, the type\'s instances (objects whose `~PyObject.ob_type`{.interpreted-text role="c:member"} points back to the type) do *not* count as references. But for `dynamically allocated type objects <heap-types>`{.interpreted-text role="ref"}, the instances *do* count as references.
>
> **Inheritance:**
>
> This field is not inherited by subtypes.

`PyObject.ob_type`{.interpreted-text role="c:member"}

> This is the type\'s type, in other words its metatype. It is initialized by the argument to the `PyObject_HEAD_INIT` macro, and its value should normally be `&PyType_Type`. However, for dynamically loadable extension modules that must be usable on Windows (at least), the compiler complains that this is not a valid initializer. Therefore, the convention is to pass `NULL` to the `PyObject_HEAD_INIT` macro and to initialize this field explicitly at the start of the module\'s initialization function, before doing anything else. This is typically done like this:
>
> ``` c
> Foo_Type.ob_type = &PyType_Type;
> ```
>
> This should be done before any instances of the type are created. `PyType_Ready`{.interpreted-text role="c:func"} checks if `~PyObject.ob_type`{.interpreted-text role="c:member"} is `NULL`, and if so, initializes it to the `~PyObject.ob_type`{.interpreted-text role="c:member"} field of the base class. `PyType_Ready`{.interpreted-text role="c:func"} will not change this field if it is non-zero.
>
> **Inheritance:**
>
> This field is inherited by subtypes.

## PyVarObject Slots

`PyVarObject.ob_size`{.interpreted-text role="c:member"}

> For `statically allocated type objects <static-types>`{.interpreted-text role="ref"}, this should be initialized to zero. For `dynamically allocated type objects

## PyTypeObject Slots

Each slot has a section describing inheritance. If `PyType_Ready`{.interpreted-text role="c:func"} may set a value when the field is set to `NULL` then there will also be a \"Default\" section. (Note that many fields set on `PyBaseObject_Type`{.interpreted-text role="c:data"} and `PyType_Type`{.interpreted-text role="c:data"} effectively act as defaults.)

> Pointer to a NUL-terminated string containing the name of the type. For types that are accessible as module globals, the string should be the full module name, followed by a dot, followed by the type name; for built-in types, it should be just the type name. If the module is a submodule of a package, the full package name is part of the full module name. For example, a type named `!T`{.interpreted-text role="class"} defined in module `!M`{.interpreted-text role="mod"} in subpackage `!Q`{.interpreted-text role="mod"} in package `!P`{.interpreted-text role="mod"} should have the `~PyTypeObject.tp_name`{.interpreted-text role="c:member"} initializer `"P.Q.M.T"`.
>
> For `dynamically allocated type objects <heap-types>`{.interpreted-text role="ref"}, this should just be the type name, and the module name explicitly stored in the type dict as the value for key `'__module__'`.
>
> For `statically allocated type objects <static-types>`{.interpreted-text role="ref"}, the *tp_name* field should contain a dot. Everything before the last dot is made accessible as the `~type.__module__`{.interpreted-text role="attr"} attribute, and everything after the last dot is made accessible as the `~type.__name__`{.interpreted-text role="attr"} attribute.
>
> If no dot is present, the entire `~PyTypeObject.tp_name`{.interpreted-text role="c:member"} field is made accessible as the `~type.__name__`{.interpreted-text role="attr"} attribute, and the `~type.__module__`{.interpreted-text role="attr"} attribute is undefined (unless explicitly set in the dictionary, as explained above). This means your type will be impossible to pickle. Additionally, it will not be listed in module documentations created with pydoc.
>
> This field must not be `NULL`. It is the only required field in `PyTypeObject`{.interpreted-text role="c:func"} (other than potentially `~PyTypeObject.tp_itemsize`{.interpreted-text role="c:member"}).
>
> **Inheritance:**
>
> This field is not inherited by subtypes.

> ::: corresponding-type-slot
> Py_tp_dealloc
> :::
>
> A pointer to the instance destructor function. The function signature is:
>
> ``` c
> void tp_dealloc(PyObject *self);
> ```
>
> The destructor function should remove all references which the instance owns (e.g., call `Py_CLEAR`{.interpreted-text role="c:func"}), free all memory buffers owned by the instance, and call the type\'s `~PyTypeObject.tp_free`{.interpreted-text role="c:member"} function to free the object itself.
>
> If you may call functions that may set the error indicator, you must use `PyErr_GetRaisedException`{.interpreted-text role="c:func"} and `PyErr_SetRaisedException`{.interpreted-text role="c:func"} to ensure you don\'t clobber a preexisting error indicator (the deallocation could have occurred while processing a different error):
>
> ``` c
> static void
> foo_dealloc(foo_object *self)
> {
>     PyObject *et, *ev, *etb;
>     PyObject *exc = PyErr_GetRaisedException();
>     ...
>     PyErr_SetRaisedException(exc);
> }
> ```
>
> The dealloc handler itself must not raise an exception; if it hits an error case it should call `PyErr_FormatUnraisable`{.interpreted-text role="c:func"} to log (and clear) an unraisable exception.
>
> No guarantees are made about when an object is destroyed, except:
>
> - Python will destroy an object immediately or some time after the final reference to the object is deleted, unless its finalizer (`~PyTypeObject.tp_finalize`{.interpreted-text role="c:member"}) subsequently resurrects the object.
> - An object will not be destroyed while it is being automatically finalized (`~PyTypeObject.tp_finalize`{.interpreted-text role="c:member"}) or automatically cleared (`~PyTypeObject.tp_clear`{.interpreted-text role="c:member"}).
>
> CPython currently destroys an object immediately from `Py_DECREF`{.interpreted-text role="c:func"} when the new reference count is zero, but this may change in a future version.
>
> It is recommended to call `PyObject_CallFinalizerFromDealloc`{.interpreted-text role="c:func"} at the beginning of `!tp_dealloc`{.interpreted-text role="c:member"} to guarantee that the object is always finalized before destruction.
>
> If the type supports garbage collection (the `Py_TPFLAGS_HAVE_GC`{.interpreted-text role="c:macro"} flag is set), the destructor should call `PyObject_GC_UnTrack`{.interpreted-text role="c:func"} before clearing any member fields.
>
> It is permissible to call `~PyTypeObject.tp_clear`{.interpreted-text role="c:member"} from `!tp_dealloc`{.interpreted-text role="c:member"} to reduce code duplication and to guarantee that the object is always cleared before destruction. Beware that `!tp_clear`{.interpreted-text role="c:member"} might have already been called.
>
> If the type is heap allocated (`Py_TPFLAGS_HEAPTYPE`{.interpreted-text role="c:macro"}), the deallocator should release the owned reference to its type object (via `Py_DECREF`{.interpreted-text role="c:func"}) after calling the type deallocator. See the example code below.:
>
> ``` c
> static void
> foo_dealloc(PyObject *op)
> {
>    foo_object *self = (foo_object *) op;
>    PyObject_GC_UnTrack(self);
>    Py_CLEAR(self->ref);
>    Py_TYPE(self)->tp_free(self);
> }
> ```
>
> `!tp_dealloc`{.interpreted-text role="c:member"} must leave the exception status unchanged. If it needs to call something that might raise an exception, the exception state must be backed up first and restored later (after logging any exceptions with `PyErr_WriteUnraisable`{.interpreted-text role="c:func"}).
>
> Example:
>
> ``` c
> static void
> foo_dealloc(PyObject *self)
> {
>     PyObject *exc = PyErr_GetRaisedException();
>
>     if (PyObject_CallFinalizerFromDealloc(self) < 0) {
>         // self was resurrected.
>         goto done;
>     }
>
>     PyTypeObject *tp = Py_TYPE(self);
>
>     if (tp->tp_flags & Py_TPFLAGS_HAVE_GC) {
>         PyObject_GC_UnTrack(self);
>     }
>
>     // Optional, but convenient to avoid code duplication.
>     if (tp->tp_clear && tp->tp_clear(self) < 0) {
>         PyErr_WriteUnraisable(self);
>     }
>
>     // Any additional destruction goes here.
>
>     tp->tp_free(self);
>     self = NULL;  // In case PyErr_WriteUnraisable() is called below.
>
>     if (tp->tp_flags & Py_TPFLAGS_HEAPTYPE) {
>         Py_CLEAR(tp);
>     }
>
> done:
>     // Optional, if something was called that might have raised an
>     // exception.
>     if (PyErr_Occurred()) {
>         PyErr_WriteUnraisable(self);
>     }
>     PyErr_SetRaisedException(exc);
> }
> ```
>
> `!tp_dealloc`{.interpreted-text role="c:member"} may be called from any Python thread, not just the thread which created the object (if the object becomes part of a refcount cycle, that cycle might be collected by a garbage collection on any thread). This is not a problem for Python API calls, since the thread on which `!tp_dealloc`{.interpreted-text role="c:member"} is called with an `attached thread state`{.interpreted-text role="term"}. However, if the object being destroyed in turn destroys objects from some other C library, care should be taken to ensure that destroying those objects on the thread which called `!tp_dealloc`{.interpreted-text role="c:member"} will not violate any assumptions of the library.
>
> **Inheritance:**
>
> This field is inherited by subtypes.
>

> :::

> ::: corresponding-type-slot
> Py_tp_traverse
> :::
>
> An optional pointer to a traversal function for the garbage collector. This is only used if the `Py_TPFLAGS_HAVE_GC`{.interpreted-text role="c:macro"} flag bit is set. The signature is:
>
> ``` c
> int tp_traverse(PyObject *self, visitproc visit, void *arg);
> ```
>
> More information about Python\'s garbage collection scheme can be found in section `supporting-cycle-detection`{.interpreted-text role="ref"}.
>
> The `~PyTypeObject.tp_traverse`{.interpreted-text role="c:member"} pointer is used by the garbage collector to detect reference cycles. A typical implementation of a `~PyTypeObject.tp_traverse`{.interpreted-text role="c:member"} function simply calls `Py_VISIT`{.interpreted-text role="c:func"} on each of the instance\'s members that are Python objects that the instance owns. For example, this is function `!local_traverse`{.interpreted-text role="c:func"} from the `!_thread`{.interpreted-text role="mod"} extension module:
>
> ``` c
> static int
> local_traverse(PyObject *op, visitproc visit, void *arg)
> {
>     localobject *self = (localobject *) op;
>     Py_VISIT(self->args);
>     Py_VISIT(self->kw);
>     Py_VISIT(self->dict);
>     return 0;
> }
> ```
>
> Note that `Py_VISIT`{.interpreted-text role="c:func"} is called only on those members that can participate in reference cycles. Although there is also a `self->key` member, it can only be `NULL` or a Python string and therefore cannot be part of a reference cycle.
>
> On the other hand, even if you know a member can never be part of a cycle, as a debugging aid you may want to visit it anyway just so the `gc`{.interpreted-text role="mod"} module\'s `~gc.get_referents`{.interpreted-text role="func"} function will include it.
>
> Heap types (`Py_TPFLAGS_HEAPTYPE`{.interpreted-text role="c:macro"}) must visit their type with:
>
> ``` c
> Py_VISIT(Py_TYPE(self));
> ```
>
> It is only needed since Python 3.9. To support Python 3.8 and older, this line must be conditional:
>
> ``` c
> #if PY_VERSION_HEX >= 0x03090000
>     Py_VISIT(Py_TYPE(self));
> #endif
> ```
>
> If the `Py_TPFLAGS_MANAGED_DICT`{.interpreted-text role="c:macro"} bit is set in the `~PyTypeObject.tp_flags`{.interpreted-text role="c:member"} field, the traverse function must call `PyObject_VisitManagedDict`{.interpreted-text role="c:func"} like this:
>
> ``` c
> PyObject_VisitManagedDict((PyObject*)self, visit, arg);
> ```
>
> :::: warning
> ::: title
> Warning
> :::
>
> When implementing `~PyTypeObject.tp_traverse`{.interpreted-text role="c:member"}, only the members that the instance *owns* (by having `strong references
> <strong reference>`{.interpreted-text role="term"} to them) must be visited. For instance, if an object supports weak references via the `~PyTypeObject.tp_weaklist`{.interpreted-text role="c:member"} slot, the pointer supporting the linked list (what *tp_weaklist* points to) must **not** be visited as the instance does not directly own the weak references to itself (the weakreference list is there to support the weak reference machinery, but the instance has no strong reference to the elements inside it, as they are allowed to be removed even if the instance is still alive).
> ::::
>
> :::: warning
> ::: title
> Warning
> :::
>
> The traversal function must not have any side effects. It must not modify the reference counts of any Python objects nor create or destroy any Python objects.
> ::::
>
> Note that `Py_VISIT`{.interpreted-text role="c:func"} requires the *visit* and *arg* parameters to `!local_traverse`{.interpreted-text role="c:func"} to have these specific names; don\'t name them just anything.
>
> Instances of `heap-allocated types <heap-types>`{.interpreted-text role="ref"} hold a reference to their type. Their traversal function must therefore either visit `Py_TYPE(self) <Py_TYPE>`{.interpreted-text role="c:func"}, or delegate this responsibility by calling `tp_traverse` of another heap-allocated type (such as a heap-allocated superclass). If they do not, the type object may not be garbage-collected.
>
> :::: note
> ::: title
> Note
> :::
>
> The `~PyTypeObject.tp_traverse`{.interpreted-text role="c:member"} function can be called from any thread.
> ::::

>

> ::: corresponding-type-slot
> Py_tp_clear
> :::
>
> An optional pointer to a clear function. The signature is:
>
> ``` c
> int tp_clear(PyObject *);
> ```
>
> The purpose of this function is to break reference cycles that are causing a `cyclic isolate`{.interpreted-text role="term"} so that the objects can be safely destroyed. A cleared object is a partially destroyed object; the object is not obligated to satisfy design invariants held during normal use.
>
> `!tp_clear`{.interpreted-text role="c:member"} does not need to delete references to objects that can\'t participate in reference cycles, such as Python strings or Python integers. However, it may be convenient to clear all references, and write the type\'s `~PyTypeObject.tp_dealloc`{.interpreted-text role="c:member"} function to invoke `!tp_clear`{.interpreted-text role="c:member"} to avoid code duplication. (Beware that `!tp_clear`{.interpreted-text role="c:member"} might have already been called. Prefer calling idempotent functions like `Py_CLEAR`{.interpreted-text role="c:func"}.)
>
> Any non-trivial cleanup should be performed in `~PyTypeObject.tp_finalize`{.interpreted-text role="c:member"} instead of `!tp_clear`{.interpreted-text role="c:member"}.
>
> :::: note
> ::: title
> Note
> :::
>
> If `!tp_clear`{.interpreted-text role="c:member"} fails to break a reference cycle then the objects in the `cyclic isolate`{.interpreted-text role="term"} may remain indefinitely uncollectable (\"leak\"). See `gc.garbage`{.interpreted-text role="data"}.
> ::::
>
> :::: note
> ::: title
> Note
> :::
>
> Referents (direct and indirect) might have already been cleared; they are not guaranteed to be in a consistent state.
> ::::
>
> :::: note
> ::: title
> Note
> :::
>
> The `~PyTypeObject.tp_clear`{.interpreted-text role="c:member"} function can be called from any thread.
> ::::
>
> :::: note
> ::: title
> Note
> :::
>
> An object is not guaranteed to be automatically cleared before its destructor (`~PyTypeObject.tp_dealloc`{.interpreted-text role="c:member"}) is called.
> ::::
>
> This function differs from the destructor (`~PyTypeObject.tp_dealloc`{.interpreted-text role="c:member"}) in the following ways:
>
> - The purpose of clearing an object is to remove references to other objects that might participate in a reference cycle. The purpose of the destructor, on the other hand, is a superset: it must release *all* resources it owns, including references to objects that cannot participate in a reference cycle (e.g., integers) as well as the object\'s own memory (by calling `~PyTypeObject.tp_free`{.interpreted-text role="c:member"}).
> - When `!tp_clear`{.interpreted-text role="c:member"} is called, other objects might still hold references to the object being cleared. Because of this, `!tp_clear`{.interpreted-text role="c:member"} must not deallocate the object\'s own memory (`~PyTypeObject.tp_free`{.interpreted-text role="c:member"}). The destructor, on the other hand, is only called when no (strong) references exist, and as such, must safely destroy the object itself by deallocating it.
> - `!tp_clear`{.interpreted-text role="c:member"} might never be automatically called. An object\'s destructor, on the other hand, will be automatically called some time after the object becomes unreachable (i.e., either there are no references to the object or the object is a member of a `cyclic isolate`{.interpreted-text role="term"}).
>
> No guarantees are made about when, if, or how often Python automatically clears an object, except:
>
> - Python will not automatically clear an object if it is reachable, i.e., there is a reference to it and it is not a member of a `cyclic
>   isolate`{.interpreted-text role="term"}.
> - Python will not automatically clear an object if it has not been automatically finalized (see `~PyTypeObject.tp_finalize`{.interpreted-text role="c:member"}). (If the finalizer resurrected the object, the object may or may not be automatically finalized again before it is cleared.)
> - If an object is a member of a `cyclic isolate`{.interpreted-text role="term"}, Python will not automatically clear it if any member of the cyclic isolate has not yet been automatically finalized (`~PyTypeObject.tp_finalize`{.interpreted-text role="c:member"}).
> - Python will not destroy an object until after any automatic calls to its `!tp_clear`{.interpreted-text role="c:member"} function have returned. This ensures that the act of breaking a reference cycle does not invalidate the `self` pointer while `!tp_clear`{.interpreted-text role="c:member"} is still executing.
> - Python will not automatically call `!tp_clear`{.interpreted-text role="c:member"} multiple times concurrently.
>
> CPython currently only automatically clears objects as needed to break reference cycles in a `cyclic isolate`{.interpreted-text role="term"}, but future versions might clear objects regularly before their destruction.
>
> Taken together, all `~PyTypeObject.tp_clear`{.interpreted-text role="c:member"} functions in the system must combine to break all reference cycles. This is subtle, and if in any doubt supply a `~PyTypeObject.tp_clear`{.interpreted-text role="c:member"} function. For example, the tuple type does not implement a `~PyTypeObject.tp_clear`{.interpreted-text role="c:member"} function, because it\'s possible to prove that no reference cycle can be composed entirely of tuples. Therefore the `~PyTypeObject.tp_clear`{.interpreted-text role="c:member"} functions of other types are responsible for breaking any cycle containing a tuple. This isn\'t immediately obvious, and there\'s rarely a good reason to avoid implementing `~PyTypeObject.tp_clear`{.interpreted-text role="c:member"}.
>
> Implementations of `~PyTypeObject.tp_clear`{.interpreted-text role="c:member"} should drop the instance\'s references to those of its members that may be Python objects, and set its pointers to those members to `NULL`, as in the following example:
>
> ``` c
> static int
> local_clear(PyObject *op)
> {
>     localobject *self = (localobject *) op;
>     Py_CLEAR(self->key);
>     Py_CLEAR(self->args);
>     Py_CLEAR(self->kw);
>     Py_CLEAR(self->dict);
>     return 0;
> }
> ```
>
> The `Py_CLEAR`{.interpreted-text role="c:func"} macro should be used, because clearing references is delicate: the reference to the contained object must not be released (via `Py_DECREF`{.interpreted-text role="c:func"}) until after the pointer to the contained object is set to `NULL`. This is because releasing the reference may cause the contained object to become trash, triggering a chain of reclamation activity that may include invoking arbitrary Python code (due to finalizers, or weakref callbacks, associated with the contained object). If it\'s possible for such code to reference *self* again, it\'s important that the pointer to the contained object be `NULL` at that time, so that *self* knows the contained object can no longer be used. The `Py_CLEAR`{.interpreted-text role="c:func"} macro performs the operations in a safe order.
>
> If the `Py_TPFLAGS_MANAGED_DICT`{.interpreted-text role="c:macro"} bit is set in the `~PyTypeObject.tp_flags`{.interpreted-text role="c:member"} field, the clear function must call `PyObject_ClearManagedDict`{.interpreted-text role="c:func"} like this:
>
> ``` c
> PyObject_ClearManagedDict((PyObject*)self);
> ```
>
> More information about Python\'s garbage collection scheme can be found in section `supporting-cycle-detection`{.interpreted-text role="ref"}.
>
> **Inheritance:**
>
> Group: `Py_TPFLAGS_HAVE_GC`{.interpreted-text role="c:macro"}, `~PyTypeObject.tp_traverse`{.interpreted-text role="c:member"}, `~PyTypeObject.tp_clear`{.interpreted-text role="c:member"}
>
> This field is inherited by subtypes together with `~PyTypeObject.tp_traverse`{.interpreted-text role="c:member"} and the `Py_TPFLAGS_HAVE_GC`{.interpreted-text role="c:macro"} flag bit: the flag bit, `~PyTypeObject.tp_traverse`{.interpreted-text role="c:member"}, and `~PyTypeObject.tp_clear`{.interpreted-text role="c:member"} are all inherited from the base type if they are all zero in the subtype.

> ::: corresponding-type-slot
> Py_tp_finalize
> :::
>
> An optional pointer to an instance finalization function. This is the C implementation of the `~object.__del__`{.interpreted-text role="meth"} special method. Its signature is:
>
> ``` c
> void tp_finalize(PyObject *self);
> ```
>
> The primary purpose of finalization is to perform any non-trivial cleanup that must be performed before the object is destroyed, while the object and any other objects it directly or indirectly references are still in a consistent state. The finalizer is allowed to execute arbitrary Python code.
>
> Before Python automatically finalizes an object, some of the object\'s direct or indirect referents might have themselves been automatically finalized. However, none of the referents will have been automatically cleared (`~PyTypeObject.tp_clear`{.interpreted-text role="c:member"}) yet.
>
> Other non-finalized objects might still be using a finalized object, so the finalizer must leave the object in a sane state (e.g., invariants are still met).
>
> :::: note
> ::: title
> Note
> :::
>
> After Python automatically finalizes an object, Python might start automatically clearing (`~PyTypeObject.tp_clear`{.interpreted-text role="c:member"}) the object and its referents (direct and indirect). Cleared objects are not guaranteed to be in a consistent state; a finalized object must be able to tolerate cleared referents.
> ::::
>
> :::: note
> ::: title
> Note
> :::
>
> An object is not guaranteed to be automatically finalized before its destructor (`~PyTypeObject.tp_dealloc`{.interpreted-text role="c:member"}) is called. It is recommended to call `PyObject_CallFinalizerFromDealloc`{.interpreted-text role="c:func"} at the beginning of `!tp_dealloc`{.interpreted-text role="c:member"} to guarantee that the object is always finalized before destruction.
> ::::
>
> :::: note
> ::: title
> Note
> :::
>
> The `~PyTypeObject.tp_finalize`{.interpreted-text role="c:member"} function can be called from any thread, although the `GIL`{.interpreted-text role="term"} will be held.
> ::::
>
> :::: note
> ::: title
> Note
> :::
>
> The `!tp_finalize`{.interpreted-text role="c:member"} function can be called during shutdown, after some global variables have been deleted. See the documentation of the `~object.__del__`{.interpreted-text role="meth"} method for details.
> ::::
>
> When Python finalizes an object, it behaves like the following algorithm:
>
> 1.  Python might mark the object as *finalized*. Currently, Python always marks objects whose type supports garbage collection (i.e., the `Py_TPFLAGS_HAVE_GC`{.interpreted-text role="c:macro"} flag is set in `~PyTypeObject.tp_flags`{.interpreted-text role="c:member"}) and never marks other types of objects; this might change in a future version.
> 2.  If the object is not marked as *finalized* and its `!tp_finalize`{.interpreted-text role="c:member"} finalizer function is non-`NULL`, the finalizer function is called.
> 3.  If the finalizer function was called and the finalizer made the object reachable (i.e., there is a reference to the object and it is not a member of a `cyclic isolate`{.interpreted-text role="term"}), then the finalizer is said to have *resurrected* the object. It is unspecified whether the finalizer can also resurrect the object by adding a new reference to the object that does not make it reachable, i.e., the object is (still) a member of a cyclic isolate.
> 4.  If the finalizer resurrected the object, the object\'s pending destruction is canceled and the object\'s *finalized* mark might be removed if present. Currently, Python never removes the *finalized* mark; this might change in a future version.
>
> *Automatic finalization* refers to any finalization performed by Python except via calls to `PyObject_CallFinalizer`{.interpreted-text role="c:func"} or `PyObject_CallFinalizerFromDealloc`{.interpreted-text role="c:func"}. No guarantees are made about when, if, or how often an object is automatically finalized, except:
>
> - Python will not automatically finalize an object if it is reachable, i.e., there is a reference to it and it is not a member of a `cyclic
>   isolate`{.interpreted-text role="term"}.
> - Python will not automatically finalize an object if finalizing it would not mark the object as *finalized*. Currently, this applies to objects whose type does not support garbage collection, i.e., the `Py_TPFLAGS_HAVE_GC`{.interpreted-text role="c:macro"} flag is not set. Such objects can still be manually finalized by calling `PyObject_CallFinalizer`{.interpreted-text role="c:func"} or `PyObject_CallFinalizerFromDealloc`{.interpreted-text role="c:func"}.
> - Python will not automatically finalize any two members of a `cyclic
>   isolate`{.interpreted-text role="term"} concurrently.
> - Python will not automatically finalize an object after it has automatically cleared (`~PyTypeObject.tp_clear`{.interpreted-text role="c:member"}) the object.
> - If an object is a member of a `cyclic isolate`{.interpreted-text role="term"}, Python will not automatically finalize it after automatically clearing (see `~PyTypeObject.tp_clear`{.interpreted-text role="c:member"}) any other member.
> - Python will automatically finalize every member of a `cyclic
>   isolate`{.interpreted-text role="term"} before it automatically clears (see `~PyTypeObject.tp_clear`{.interpreted-text role="c:member"}) any of them.
> - If Python is going to automatically clear an object (`~PyTypeObject.tp_clear`{.interpreted-text role="c:member"}), it will automatically finalize the object first.
>
> Python currently only automatically finalizes objects that are members of a `cyclic isolate`{.interpreted-text role="term"}, but future versions might finalize objects regularly before their destruction.
>
> To manually finalize an object, do not call this function directly; call `PyObject_CallFinalizer`{.interpreted-text role="c:func"} or `PyObject_CallFinalizerFromDealloc`{.interpreted-text role="c:func"} instead.
>
> `~PyTypeObject.tp_finalize`{.interpreted-text role="c:member"} should leave the current exception status unchanged. The recommended way to write a non-trivial finalizer is to back up the exception at the beginning by calling `PyErr_GetRaisedException`{.interpreted-text role="c:func"} and restore the exception at the end by calling `PyErr_SetRaisedException`{.interpreted-text role="c:func"}. If an exception is encountered in the middle of the finalizer, log and clear it with `PyErr_WriteUnraisable`{.interpreted-text role="c:func"} or `PyErr_FormatUnraisable`{.interpreted-text role="c:func"}. For example:
>
> ``` c
> static void
> foo_finalize(PyObject *self)
> {
>     // Save the current exception, if any.
>     PyObject *exc = PyErr_GetRaisedException();
>
>     // ...
>
>     if (do_something_that_might_raise() != success_indicator) {
>         PyErr_WriteUnraisable(self);
>         goto done;
>     }
>
> done:
>     // Restore the saved exception.  This silently discards any exception
>     // raised above, so be sure to call PyErr_WriteUnraisable first if
>     // necessary.
>     PyErr_SetRaisedException(exc);
> }
> ```
>
> **Inheritance:**
>
> This field is inherited by subtypes.
>
> ::: versionadded
> 3.4
> :::
>
> ::: versionchanged
> 3.8
>
> Before version 3.8 it was necessary to set the `Py_TPFLAGS_HAVE_FINALIZE`{.interpreted-text role="c:macro"} flags bit in order for this field to be used. This is no longer required.
> :::

> :::: note

When doing this for user-subclassable types, note that both can be overridden (using `~object.__new__`{.interpreted-text role="py:func"} and `~object.__init__`{.interpreted-text role="py:func"}, respectively).

## Static Types

Traditionally, types defined in C code are *static*, that is, a static `PyTypeObject`{.interpreted-text role="c:type"} structure is defined directly in code and initialized using `PyType_Ready`{.interpreted-text role="c:func"}.

This results in types that are limited relative to types defined in Python:

- Static types are limited to one base, i.e. they cannot use multiple inheritance.
- Static type objects (but not necessarily their instances) are immutable. It is not possible to add or modify the type object\'s attributes from Python.
- Static type objects are shared across `sub-interpreters <sub-interpreter-support>`{.interpreted-text role="ref"}, so they should not include any subinterpreter-specific state.

Also, since `PyTypeObject`{.interpreted-text role="c:type"} is only part of the `Limited API
<limited-c-api>`{.interpreted-text role="ref"} as an opaque struct, any extension modules using static types must be compiled for a specific Python minor version.

## Heap Types

An alternative to `static types <static-types>`{.interpreted-text role="ref"} is *heap-allocated types*, or *heap types* for short, which correspond closely to classes created by Python\'s `class` statement. Heap types have the `Py_TPFLAGS_HEAPTYPE`{.interpreted-text role="c:macro"} flag set.

This is done by filling a `PyType_Spec`{.interpreted-text role="c:type"} structure and calling `PyType_FromSpec`{.interpreted-text role="c:func"}, `PyType_FromSpecWithBases`{.interpreted-text role="c:func"}, `PyType_FromModuleAndSpec`{.interpreted-text role="c:func"}, or `PyType_FromMetaclass`{.interpreted-text role="c:func"}.

It is also used by the augmented assignment `*=`, after trying numeric in-place multiplication via the `~PyNumberMethods.nb_inplace_multiply`{.interpreted-text role="c:member"} slot.

## Buffer Object Structures {#buffer-structs}

> This structure holds pointers to the functions required by the `Buffer protocol <bufferobjects>`{.interpreted-text role="ref"}. The protocol defines how an exporter object can expose its internal data to consumer objects.

> ::: corresponding-type-slot
> Py_bf_getbuffer
> :::
>
> The signature of this function is:
>
> ``` c
> int (PyObject *exporter, Py_buffer *view, int flags);
> ```
>
> Handle a request to *exporter* to fill in *view* as specified by *flags*. Except for point (3), an implementation of this function MUST take these steps:
>
> (1) Check if the request can be met. If not, raise `BufferError`{.interpreted-text role="exc"}, set `view->obj`{.interpreted-text role="c:expr"} to `NULL` and return `-1`.
> (2) Fill in the requested fields.
> (3) Increment an internal counter for the number of exports.
> (4) Set `view->obj`{.interpreted-text role="c:expr"} to *exporter* and increment `view->obj`{.interpreted-text role="c:expr"}.
> (5) Return `0`.
>
> If *exporter* is part of a chain or tree of buffer providers, two main schemes can be used:
>
> - Re-export: Each member of the tree acts as the exporting object and sets `view->obj`{.interpreted-text role="c:expr"} to a new reference to itself.
> - Redirect: The buffer request is redirected to the root object of the tree. Here, `view->obj`{.interpreted-text role="c:expr"} will be a new reference to the root object.
>
> The individual fields of *view* are described in section `Buffer structure <buffer-structure>`{.interpreted-text role="ref"}, the rules how an exporter must react to specific requests are in section `Buffer request types <buffer-request-types>`{.interpreted-text role="ref"}.
>
> All memory pointed to in the `Py_buffer`{.interpreted-text role="c:type"} structure belongs to the exporter and must remain valid until there are no consumers left. `~Py_buffer.format`{.interpreted-text role="c:member"}, `~Py_buffer.shape`{.interpreted-text role="c:member"}, `~Py_buffer.strides`{.interpreted-text role="c:member"}, `~Py_buffer.suboffsets`{.interpreted-text role="c:member"} and `~Py_buffer.internal`{.interpreted-text role="c:member"} are read-only for the consumer.
>
> `PyBuffer_FillInfo`{.interpreted-text role="c:func"} provides an easy way of exposing a simple bytes buffer while dealing correctly with all request types.
>
> `PyObject_GetBuffer`{.interpreted-text role="c:func"} is the interface for the consumer that wraps this function.

> ::: corresponding-type-slot
> Py_bf_releasebuffer
> :::
>
> The signature of this function is:
>
> ``` c
> void (PyObject *exporter, Py_buffer *view);
> ```
>
> Handle a request to release the resources of the buffer. If no resources need to be released, `PyBufferProcs.bf_releasebuffer`{.interpreted-text role="c:member"} may be `NULL`. Otherwise, a standard implementation of this function will take these optional steps:
>
> (1) Decrement an internal counter for the number of exports.
> (2) If the counter is `0`, free all memory associated with *view*.
>
> The exporter MUST use the `~Py_buffer.internal`{.interpreted-text role="c:member"} field to keep track of buffer-specific resources. This field is guaranteed to remain constant, while a consumer MAY pass a copy of the original buffer as the *view* argument.
>
> This function MUST NOT decrement `view->obj`{.interpreted-text role="c:expr"}, since that is done automatically in `PyBuffer_Release`{.interpreted-text role="c:func"} (this scheme is useful for breaking reference cycles).
>
> `PyBuffer_Release`{.interpreted-text role="c:func"} is the interface for the consumer that wraps this function.

## Examples {#typedef-examples}

The following are simple examples of Python type definitions. They include common usage you may encounter. Some demonstrate tricky corner cases. For more examples, practical info, and a tutorial, see `defining-new-types`{.interpreted-text role="ref"} and `new-types-topics`{.interpreted-text role="ref"}.

A basic `static type <static-types>`{.interpreted-text role="ref"}:

``` c
typedef struct {
    PyObject_HEAD
    const char *data;
} MyObject;

static PyTypeObject MyObject_Type = {
    PyVarObject_HEAD_INIT(NULL, 0)
    .tp_name = "mymod.MyObject",
    .tp_basicsize = sizeof(MyObject),
    .tp_doc = PyDoc_STR("My objects"),
    .tp_new = myobj_new,
    .tp_dealloc = (destructor)myobj_dealloc,
    .tp_repr = (reprfunc)myobj_repr,
};
```

A type that supports weakrefs, instance dicts, and hashing:

``` c
typedef struct {

static PyTypeObject MyObject_Type = {

    .tp_doc = PyDoc_STR("My objects"),
    .tp_flags = Py_TPFLAGS_DEFAULT | Py_TPFLAGS_BASETYPE |
         Py_TPFLAGS_HAVE_GC | Py_TPFLAGS_MANAGED_DICT |
         Py_TPFLAGS_MANAGED_WEAKREF,
    .tp_new = myobj_new,
    .tp_traverse = (traverseproc)myobj_traverse,
```

The simplest `static type <static-types>`{.interpreted-text role="ref"} with variable-length instances:

``` c
typedef struct {
    PyObject_VAR_HEAD
    const char *data[1];
} MyObject;

static PyTypeObject MyObject_Type = {
    PyVarObject_HEAD_INIT(NULL, 0)
    .tp_name = "mymod.MyObject",
    .tp_basicsize = sizeof(MyObject) - sizeof(char *),
    .tp_itemsize = sizeof(char *),
};
```

[^1]: **()**: A slot name in parentheses indicates it is (effectively) deprecated.

    **\<\>**: Names in angle brackets should be initially set to `NULL` and treated as read-only.

    **\[\]**: Names in square brackets are for internal use only.

    **\<R\>** (as a prefix) means the field is required (must be non-`NULL`).

[^2]: Columns:

    **\"O\"**: set on `PyBaseObject_Type`{.interpreted-text role="c:data"}

    **\"T\"**: set on `PyType_Type`{.interpreted-text role="c:data"}

    **\"D\"**: default (if slot is set to `NULL`)

    ``` none
    X - PyType_Ready sets this value if it is NULL
    ~ - PyType_Ready always sets this value (it should be NULL)
    ? - PyType_Ready may set this value depending on other slots

    Also see the inheritance column ("I").
    ```

    **\"I\"**: inheritance

    ``` none
    X - type slot is inherited via *PyType_Ready* if defined with a *NULL* value
    % - the slots of the sub-struct are inherited individually
    G - inherited, but only in combination with other slots; see the slot's description
    ? - it's complicated; see the slot's description
    ```

    Note that some slots are effectively inherited through the normal attribute lookup chain.
